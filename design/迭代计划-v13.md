## 1. 范围界定（先钉死「角色选项」）

### 1.1 本版「角色选项」= 什么

| 层级 | 选项集合 | 现状 | 本版目标 |
|------|----------|------|----------|
| **A. 立绘选项（P0）** | 性别池内 `PortraitArchetype`（华山/武当/少林/峨眉/丐帮/魔教/绿林/凡尘/散修） | 男 8 + 女 8 = **16**；缺女少林、男峨眉（或回落） | **每一可选脸一张独立 webp**，矩阵 **18/18**，选择器无「借脸」感 |
| **B. 出身选项（P1）** | `origins.ts` 共 **12** 条 | 仅文字名+描述，无专属卡面 | 每出身 **1** 张选项卡（小图/竖卡），入世列表可扫图辨认 |
| **C. 非本版** | 事件里每个 `choices[].text` 按钮 | 数百选项；阅读器对 choice 行刻意不插图 | **不做一事一图**；成本与包体不可接受（见 §4） |

> 若产品口头说的「角色选项」被理解成「每个抉择按钮一张图」——本文件明确 **否决为 Phase 19 交付物**，改列入调研附录的「若未来要做，成本数量级」。

### 1.2 与 Phase 18 的关系

| Phase 18 | Phase 19 |
|----------|----------|
| 薄链/事件 **高潮映射**、立绘补洞 | 角色选项 **视觉产品化**（选脸/选出身上图） |
| 事件正文旁图 | 入世/换装选择器主图 |
| 不接实时 API | **仅调研**实时 API 成本 |

可并行：若 v12 立绘两洞未合入，本版 A 柱一并收口。

## 2. 现状诊断

### 2.1 立绘选项

- 入口：`App.tsx` 入世 `portrait-picker`、局中「更换立绘」  
- 解析：`portraitUrlFor(gender, look)` → `public/assets/portrait/p_{m|f}_{arch}.webp`  
- 标签：`PORTRAIT_LABELS`  
- 债：矩阵洞、缩略图偏小难辨门派符号、无「选项说明图」以外的差异化（同原型仅一脸）

### 2.2 出身选项

- `getOrigin` + 文字 lead；重开换出身时 **无图锚**  
- 出身影响属性/早期池，视觉上「选项感」弱于立绘

### 2.3 实时生图（现状）

- 全站 **静态 webp**；分享卡 canvas 本地拼  
- 无第三方视觉 API；符合过往「不做实时文生图」决策  
- 本版 **维持不实施**，只输出可决策的成本/合规备忘

## 3. 本阶段战略

### 3.1 两柱目标

| 目标 | 玩家体感 | 抓手 | 优先级 |
|------|----------|------|--------|
| **选项有图** | 点哪个脸/出身，预览区就是那一张，不靠文字猜 | 立绘 18 齐；出身卡 12（P1） | **P0 / P1** |
| **实时生图算清账** | 团队知道「若接 API」月费/延迟/合规，而不是拍脑袋 | 调研报告附录；**零代码接入** | **P0（调研）** |

### 3.2 设计原则

1. **一选项一主图**：选择器格子 = 最终会用于 HUD/书/分享的同一资产（或明确「选格用缩略、正文用同键大图」）  
2. **静态优先**：角色选项图进 `public/assets`，走 v5 命名  
3. **辨识度 > 画质堆料**：门派/出身符号一眼可辨  
4. **调研与交付隔离**：API 成本结论写进附录；主路径禁止偷偷加 key  
5. **不做抉择按钮配图**：与阅读器契约、包体、审核量冲突  

### 3.3 明确不做（本阶段）

| 不做 | 原因 |
|------|------|
| 接入 OpenAI/Stability/通义等实时文生图到游戏主路径 | 本版仅调研 |
| 每个事件 choice 一张图 | 选项量级 × 包体/审核爆炸 |
| 按玩家姓名实时生成脸 | 成本、审核、一致性、缓存噩梦 |
| 账号云端脸库 | 规格外 |

## 4. 产品规格

### 4.1 立绘选项一图一选项（P0）

| 项 | 规格 |
|----|------|
| 矩阵 | `p_m_*` ×9 + `p_f_*` ×9 = **18** 文件全存在 |
| 补洞 | `p_f_shaolin.webp`、`p_m_emei.webp`（若尚未交付） |
| 选择器 | 每格预览 = `portraitUrlFor`；无回落脸冒充（缺文件才允许回落并 audit 告警） |
| 一致性 | 入世预览、局中换装、HUD、书封面、分享卡同一 `portraitLook` |
| 可选增强（P1） | 选项旁一行气质短句（仍用 `PORTRAIT_LABELS` + 扩展 `PORTRAIT_BLURB`） |

**验收**：男女切换后，九个选项格均可点且图不重复借脸；女少林 ≠ 女峨眉；男峨眉 ≠ 男华山。

### 4.2 出身选项卡（P1）

| 项 | 规格 |
|----|------|
| 命名 | `public/assets/origin/o_{originId}.webp`（新目录，写入 manifest） |
| 数量 | **12**（与 `origins.ts` 同步；成就锁出身也有图，未解锁可灰显） |
| UI | 入世「出身」若为列表/重随展示，改为图文选项或结果区大图+名 |
| 风格 | 场景/器物符号卡（农具、商驿、王府门楣…），**不是第二套立绘脸** |

### 4.3 选择器 UX（P0～P1）

| 项 | 规格 |
|----|------|
| 主预览 | 当前选项大图（已有 birth-hero 可加强） |
| 网格 | 触控 ≥44px；选中态清晰 |
| 文案 | 保持「入世后不因门派自动换脸」 |

### 4.4 文生图（静态选项图）流程

沿用 v5：

```
冻结附录 A/B 清单 → 出图 webp → public/assets → manifest/单测 → UI 确认无借脸
```

本版静态出图 **允许**；实时 API **不允许**合入主路径。

## 5. 实时文生图 API 成本调研（不实施）

### 5.1 调研目标

输出一份可决策备忘（建议路径：`design/调研-实时文生图成本.md` 或本文件附录 C 填表），回答：

1. 若「入世点一次脸就生一张」——单位成本与月费区间？  
2. 若「每重大抉择生一张」——按 MAU/日局数的数量级？  
3. 延迟、审核、版权、国内可达性？  
4. 与静态资产方案的盈亏平衡（多少次生成 ≈ 雇插画/批量静图）？  
5. **结论建议**：继续静态 / 仅分享卡试验 / 明确不做（本阶段默认倾向静态）  

### 5.2 调研范围（建议厂商，可增减）

| 类型 | 候选（示例） | 关注点 |
|------|--------------|--------|
| 国际通用 | OpenAI Images、Stability、Fal.ai Flux、Replicate | 单价、分辨率档、速率限制 |
| 国内云 | 通义万相、文心、混元、火山、腾讯混元 | 备案、支付、延迟、内容审核 |
| 开源自托管 | SD/Flux 自建（仅算机器均摊，不部署） | GPU 小时成本数量级 |

### 5.3 测算假说（填表用，调研时用真实价目替换）

设产品指标（可按实改）：

| 假说 | 数值（草案） |
|------|----------------|
| 日完局数 | 200 |
| 每局入世重随立绘 | 平均 3 次预览生成 |
| 每局重大抉择若生图 | 平均 8 次 |
| 出图规格 | 1024 边、单次 1 张 |

则：

- **仅入世预览**：200 × 3 = 600 次/日  
- **若抉择也生**：200 × (3+8) = 2200 次/日  

调研表须给出：单价 × 上式 = **日/月费用区间**，并单列「失败重试 +20%」。

### 5.4 非成本维度（必写）

| 维度 | 要结论 |
|------|--------|
| 延迟 | p50/p95 是否可接受（入世等待） |
| 一致性 | 同 seed/同脸能否稳定（角色选项需要稳定脸） |
| 审核拒识 | 武侠刀剑血腥触发率 |
| 隐私与密钥 | 前端不可裸 key；若做需后端——本版仍不实施 |
| 包体 vs CDN | 静图 GitHub Pages 友好；实时图要对象存储 |

### 5.5 调研交付物与否决线

| 交付 | 说明 |
|------|------|
| 价目对比表 | 附录 C 填满「查询日 + 来源链接」 |
| 情景费用 | 入世-only / 入世+抉择 两档月费 |
| 建议一句话 | 例如：「Phase 19～20 维持静图；实时生图 ROI 不足」 |
| **代码** | **0 行接入**；禁止为调研临时写死 key |
